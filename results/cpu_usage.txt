CONCLUSION.  The layered preconditioner application occupies exactly 1.00 cores,
and exactly one OS thread accumulates CPU time in it (2.090s of the 2.094s
elapsed).  There is no multithreading in it whatsoever.  The same holds for five
applications back to back, and it is independent of the BLAS thread count.  The
dense operator is likewise serial, since FFTW.set_num_threads is never called.

The 1.50 and 1.52 figures in the default-BLAS rows are not work.  With OpenBLAS
pinned to one thread the same phases take the same wall time -- 31.62s against
31.69s for setup, 27.83s against 27.77s for the solve -- while the core count
drops to 1.14 and 1.02.  Those extra fourteen CPU-seconds are OpenBLAS worker
threads spinning at a barrier, and they buy nothing.  Reading core occupancy
without pinning BLAS would have overstated the parallelism by half.

L-sweeps, measured identically, occupies 13.75 cores in one application.  So the
diagnostic does detect threading when it is there.  Note also that it burns 20.59
CPU-seconds on work that costs 9.01s serially, a 2.3x inflation, which is why
13.75 cores yield only the 6.4x speedup measured in results/thread_scaling.txt.
