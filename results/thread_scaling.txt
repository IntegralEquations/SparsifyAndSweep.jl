Thread scaling of the two inner solvers, stage by stage (examples/thread_scaling.jl).
Converging lens, h = lambda/8, b = 8, boxes of ~64 points with pad 8.  One process
per thread count, OPENBLAS_NUM_THREADS pinned to the Julia thread count so that a
-t 1 run cannot quietly use all sixteen cores inside UMFPACK's dense kernels.
16-core Ryzen 7950X3D.

  for T in 1 4 8 16; do
    OPENBLAS_NUM_THREADS=$T julia --project=. -t $T examples/thread_scaling.jl 32 64 128 256
  done

HEADLINE: src/sweep.jl contains no threading constructs at all.  The layered sweep
is serial in both stages -- its factorization loop over slices is embarrassingly
parallel and simply is not threaded, and its application is a sequential recurrence.
It is nonetheless fast because its application does far less work: at omega/2pi=256
one layered application costs 1.97s on one core against 9.01s for one L-sweeps
application, a factor of 4.6.  L-sweeps is competitive only because it uses the
other fifteen cores.

The dense operator is the FFT convolution applied once per GMRES iteration.  The
package never calls FFTW.set_num_threads, so it is single-threaded by construction
and its cost is the same at every thread count.

--- head to head on one core, omega/2pi = 256 ---
                     factorization   one application   total at its iteration count
  layered sweep           22.57s            1.971s      22.57 +  9 x 1.971 =  40.3s
  L-sweeps                17.94s            9.012s      17.94 + 14 x 9.012 = 144.1s

On a single core the layered sweep is 3.6x faster end to end.  The entire L-sweeps
advantage reported elsewhere in this repository is the sixteen cores.

OPPORTUNITY: the slice loop in build_slab (src/sweep.jl) writes only into Alow[s],
Aup[s], naux[s] and loc[s], so it is independent per slice.  Threading it at the
3.1x L-sweeps manages would cut the layered factorization at 256 from 24.2s to
about 7.3s and make the layered sweep the faster method overall, since its solve
phase is already ahead at that frequency.
